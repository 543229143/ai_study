# 三个项目的 5 分钟讲述稿 + 追问答辩

> 用法：每个项目先讲 5 分钟（约 1100 字），然后准备接住两个最容易被问穿的问题。
> 原则：**主动交代局限**。你主动说的短板是"判断力"，被问出来的短板是"没想清楚"。

---

# 一、stock-insight（主力项目）

## 5 分钟讲述稿

**定位（30 秒）**

这是一个 A 股分析 Agent，用户用自然语言提问，它自己决定调哪些工具——行情、财务、技术指标、新闻、内部知识库——然后给出带依据的分析报告。它同时实现了四种范式：ReAct、Plan-Solve、Reflection，以及后来的原生 function calling 版，四种可以切换对比。

**为什么做这个（1 分钟）**

我做它的目的不是"做一个选股工具"，是**把 Agent 的每个零件拆开自己装一遍**。因为我发现一个现象：会用 LangChain 的人很多，但被问到"agent 卡在工具循环里怎么办""上下文涨到 8k 之后怎么压"就答不上来。这些问题只有自己从零写过一遍才有体感。所以这个项目刻意不用框架，纯 OpenAI SDK 加几百行 Python。

**架构（1.5 分钟）**

分四层：

第一层是入口，命令行，支持四种模式切换。
第二层是范式层，四种 agent 循环：ReAct 是边走边看，Plan-Solve 是先出计划再逐步执行，Reflection 是写完自评再改，第四种是原生 function calling。
第三层是工具层，十个工具，覆盖行情、财务、指标、新闻、知识库检索、关注列表、分析存档。
第四层是记忆和知识：关注列表和历史分析落 JSON，知识库是自己实现的轻量检索，按字符级 token 做倒排打分。

**关键取舍（1.5 分钟，这是重点）**

第一个取舍：**为什么一开始用文本协议**。早期 ReAct 是让模型输出 `Thought:` 和 `Action: 工具名[参数]`，我用正则去解析。这在教学上是对的——它让你看见 ReAct 的原语。但我后来量化了代价：我构造了 48 条模型真实会输出的样本，覆盖九类形态，结果 **26 条解析结果和模型意图不符，54%**。失败集中在全角冒号、多行参数被截断、圆括号、JSON 风格这几种。

第二个取舍：**换掉它，但不是因为它省钱**。换成原生 tool_calls 后，我发现 token 反而涨了：工具描述从 343 token 变成 JSON Schema 的 1205，每次调用多 862；六轮累计从 36135 涨到 41292。所以它买的不是成本，是**可靠性**——解析这一类错误不是变少，是在架构上没有可失败的地方了。当然工具选错、参数幻觉还在，只是失败从"解析层"挪到了"语义层"。

第三个取舍：**上下文压缩做得糙**。我是按字符数除以四粗估 token，超阈值就把旧轮次压成摘要，只保留最近四轮。它跑得通，但中英混排误差大，也没有做"哪些信息该保留"的语义判断。

**数据（30 秒）**

现在有 31 个单测全离线跑，覆盖工具注册、派发、异常兜底、tracer、解析器、记忆、RAG 分块。解析基准和 prompt 体积基准都可以一条命令复现。

**局限（30 秒，主动说）**

端到端的延迟和成本我**没有真实数字**。原因是这台机器既没有可用的模型 key，A 股行情接口也被网络挡住了，所以脚本我写好了、留了空表，但我不编数。这块补上只需要一个 key 和一次运行。

## 追问 Q1：你的 ReAct 用正则解析，这不是很业余吗？为什么不一开始就用 function calling？

**答：**

分三层说。

第一，一开始用文本协议是**故意的**。我要的是理解 ReAct 的原语——Thought、Action、Observation 这三件东西怎么闭环。如果直接用 function calling，模型帮你把 Action 结构化好了，你反而看不见协议本身长什么样。

第二，我后来量化了它的代价，没有靠感觉。48 条样本 54% 不符，失败集中在六类可复现的形态上，不是我瞎猜"可能有问题"。这一步很重要：**你得先能测，才能说该换**。

第三，换掉之后我犯过一个预期错误。我以为 function calling 会更省 token，实测反而每次多 862。所以我现在的表述是：它更贵，买的是可靠性。如果我当时说"我优化了 token"，一被追问 schema 开销就露馅。

最后补充一句：**旧实现我没删**，留在 `agent.py` 里做对照。因为"两种解法的差异"是我要讲的东西，删了就没法讲了。

## 追问 Q2：你说做了上下文管理，具体怎么做的？效果怎么验证的？

**答：**

做法是三层：每轮对话进一个 turn 列表；累计字符数超过阈值就触发压缩；压缩时把除最近四轮之外的内容拼成一段摘要，作为 system 消息放回去。

**验证这块我要说实话：目前只有单测覆盖"会不会触发、压缩后保留几轮"，没有质量指标。** 也就是说我知道它按设计工作，但不知道它有没有把该留的信息丢掉。

要补的话我会做两件事：一是把字符估算换成真实 tokenizer 计数，中英混排误差就不存在了；二是做一组对照——同一批问题，压与不压各跑一次，看答案完整度差多少。

还有一个更根本的改进点：现在压缩是"整段截断"，因为旧版把历史拼成一整段字符串。换成消息数组之后，其实可以**按条裁剪**——比如只丢掉旧的工具原始返回、保留结论，这样信息密度高得多。这也是我认为 function calling 真正的长期优势所在，不是省 token，是可裁剪。

# 二、column-writer（架构选型项目）

## 5 分钟讲述稿

**定位（30 秒）**

这是一个多 Agent 协作的长文写作系统。用户给一个主题，它先规划专栏结构，再按树状结构逐节写，每节写完有评审、不过就返修，最后组装成一篇完整专栏。

**为什么做这个（1 分钟）**

因为长文写作有一个和短问答完全不同的约束：**一致性**。让模型一次生成八千字，前半段和后半段经常自相矛盾，而且你没法局部修改——改一段它可能把别的段也改了。

所以我做的核心不是"让模型写得更好"，是**把长文拆成可以独立返修的单元**。这是工程问题，不是模型问题。

**架构（1.5 分钟）**

三个角色加一个编排器。

Planner 把主题拆成三到五个大章节，每个章节再拆子节，形成一棵树。
Writer 递归地写：先写当前节点，写完再递归写子节点，子节点会拿到父节点的上下文，保证不跑题。
Reviewer 对每一节打分，给出具体问题；超过返修阈值就打回。
Revision 根据评审意见重写，最多返修两次，防止无限循环。
编排器负责调度、组装、统计。

它支持四种模式切换：ReAct（边写边搜）、Reflection（写完自省）、独立评审（评审和写作分离）、以及顺序执行。这四种模式共用同一套编排，所以可以直接横向对比。

还有一个细节我比较满意：**步骤级缓存**。写作是幂等的，同样的主题、同样的步骤，结果可以缓存，重跑时直接命中，省掉重复的模型调用。这在长文场景很实用，因为一次生成可能要几分钟。

**关键取舍（1 分钟）**

第一个取舍：**树状递归 vs 一次生成**。一次生成便宜、快，但改不动；树状递归贵、慢，但每一节可以独立返修。我选后者，因为长文的核心矛盾是"改不动"。

第二个取舍：**评审要不要独立**。写和评放在同一个模型里，会出现"自我辩护"——它倾向于认为自己写得没问题。所以我把 Reviewer 拆成独立角色，用独立 prompt，只做"是否返修"的二值判断，不给主观分数。

第三个取舍：**返修上限**。不设上限会无限循环烧钱，设太小质量上不去。我设的是最多两次，超了就带着问题交付，并在报告里标注。

**数据与局限（1 分钟）**

我准备了成本对照脚本，能测出四种模式的 token、耗时、单篇成本、首稿通过率、返修次数，输出成一张表。但**这张表现在是空的**——没有 key 跑不了，我不填假数字。

已知的局限有两个：一是评审用的是 LLM 评 LLM，有自评偏好；二是"质量"目前靠评审阈值近似，没有和人工评分做过相关性验证。

## 追问 Q1：四种模式你怎么选？为什么不做成自动选？

**答：**

先说为什么不自动选：**自动选需要一个评估器，而评估器本身要花模型调用、而且不可靠**。你等于用一个不确定的东西去决定另一个不确定的东西，链路更长、更难排查。这是典型的"为了智能而增加不确定性"。

我的选法是按场景静态选：要快、要便宜，走 ReAct 顺序写；要质量、不在乎成本，走独立评审；要最少的人工干预，走 Reflection。

如果真要做自动选，我会分两步：先用离线数据集把每种模式在固定主题集上的成本和通过率标定出来，形成一张决策表；然后按"预算 + 质量下限"去查表，而不是让模型临场判断。**先标定，再路由**——这和做模型网关选型的思路是一样的。

## 追问 Q2：评审 Agent 用 LLM 评 LLM，凭什么可信？

**答：**

**它不完全可信，这是设计前提。** 我不指望它判断"文章好不好"，我只让它做两件窄的事：一是指出具体问题（哪一段缺论据、哪一处前后矛盾），二是给一个是否返修的二值判断。

把开放式的"评价"收敛成封闭式的"检查"，偏差会小很多。因为"好不好"是主观的，"这一段有没有支撑材料"是可验证的。

另外我做了两个约束：评审用独立 prompt、独立角色，不和写作共享上下文，避免自我辩护；返修有次数上限，防止它在"评审不满意—改—还是不满意"里循环烧钱。

**没做的是**：没有拿评审结果和人工评分做相关性分析。所以严格说，我只证明了这套机制能跑通、能收敛，没有证明它和人的判断一致。这是我知道的缺口，也是我下一步会补的实验——抽二十篇人工打分，算一下相关性。

# 三、sre-oncall（安全边界项目）

## 5 分钟讲述稿

**定位（30 秒）**

这是一个 SRE 告警分诊与根因调查 Agent。收到一条告警，它先出调查计划，再按计划查日志、查指标、查应急预案，最后输出一份带证据链的复盘报告。

**为什么做这个（1 分钟）**

因为运维场景和别的场景有一个本质区别：**它离"动手"太近**。分析错了只是浪费时间，但如果 Agent 有权限重启服务、扩容、回滚，那它一旦判断错，就是生产事故。

所以我做这个项目，重点不在"能不能查出来"，在**"怎么让它查得再对也不能乱动手"**。这也是我认为企业落地 Agent 最容易被忽略的一块。

**架构（1.5 分钟）**

三个阶段，串行：

第一阶段 Triage，输出一份调查计划——先查什么、用什么工具、为什么查这个。它不执行，只规划。
第二阶段 Investigation，按计划跑 ReAct 循环，调工具拿证据，直到定位根因。
第三阶段 Postmortem，把证据整理成复盘报告，先出草稿，再自我批评，再修订。

工具层有四个：日志检索、指标查询、应急预案检索，以及我后加的**修复动作**。

**关键取舍（1.5 分钟，重点）**

第一个取舍：**为什么拆三段，而不是一个大 ReAct**。一个大循环最省事，但你没法审计——你不知道它为什么查这个不查那个。拆成三段之后，计划是显式的、证据是显式的、结论是显式的，每一步都能被人复核。运维场景里，**可解释比聪明重要**。

第二个取舍：**修复动作默认拒绝，而且拒绝之后要能接着干**。这是我后来加的安全闸门。规则很简单：模型只有"提议权"，没有"执行权"。它可以说"建议重启 api-gateway"，但不能自己执行。

闸门有四种模式：默认 auto_deny 一律拒绝、suspend 挂起等人回答、prompt 当场阻塞询问、auto_approve 自动批准（只在 CI 用）。

**这里有个我后来改掉的设计**：一开始我只做了"拒绝"，但被追问"审批完了然后呢"就答不上来——人回来还得自己动手。所以我把 suspend 做成了主要路径：挂起时记下动作、理由和**这一轮的现场快照 id**，进程直接退出；人回答之后，按这个 id 取回现场接着跑，不重跑整个调查。等待期间没有进程、不烧 token。

第三个取舍：**审计留痕**。每一次提议，不管批没批，都写一行 JSONL：什么动作、什么目标、什么理由、谁决定的、什么时间。因为事后追责的时候，"模型说它没做"是不可接受的答案。

还有一个细节：被拒绝之后，Agent 不该重试，也不该换个说法再试一次。它应该退化成"给出建议步骤，交给人工"。**拒绝要改变行为，不能只是报个错。**

挂起也一样——挂起之后 Agent 不能继续试探别的动作，它必须停下，把控制权交出去。

**数据与局限（30 秒）**

13 个单测，覆盖闸门默认拒绝、非风险动作放行、审计落盘、拒绝后执行器一次都没被调用、执行器异常上报。

**最大的局限我直接说**：工具层全是 mock 数据，没接真实的 ES 和 Prometheus。所以这个项目证明的是"编排和安全边界"，不是"能查真实故障"。

## 追问 Q1：你的工具都是 mock 的，这项目有什么价值？

**答：**

价值在**编排和边界**，不在数据接入。这两件事的技术难度完全不同：接数据是体力活，编排和安全设计是判断题。

而且 mock 有个被低估的好处：**可复现**。真实日志每天都在变，你没法写回归测试；mock 数据固定，13 个单测才能稳定跑。这是测试策略的选择，不是偷懒。

真要接真实数据，改动面其实很小——工具层是接口，`LogSearchTool` 只要把 `run()` 里的查数据换成查 ES 就行，编排、审批、审计全都不用动。**我刻意把"数据源"和"决策流程"解耦了**，就是为了这个。

反过来说，如果我把精力花在接 ES 上，面试时能讲的还是"我调通了 ES"，那价值反而更低。

## 追问 Q2：Agent 提议重启服务，你怎么防止它乱来？

**答：**

三层，缺一不可。

**第一层，权限分离**：模型不持有任何执行凭据。它只能输出一个提议对象——动作、目标、理由。真正执行的那段代码在闸门后面，模型碰不到。

**第二层，默认拒绝**：闸门默认 auto_deny，风险动作白名单（重启、扩容、回滚、摘节点这些）一律先拒。要放开必须显式指定模式，而且要人批准。默认值选"拒绝"而不是"允许"，这个方向不能反。

**第三层，审计留痕**：每次提议不管结果都落 JSONL，记动作、目标、理由、决定人、时间。事后能复盘"它当时想干什么、谁批的"。注意**批准和否决各记一条**：挂起时记一条 `decided_by=suspended`，人回答后执行时再记一条 `decided_by=human`。这样审计链是完整的，不会出现"只有执行记录、不知道谁批的"。

**第四层，挂起而不是阻塞**：需要人拍板时，进程不是挂在那里等，而是把现场（run_id、动作、理由）写进挂起队列然后退出。人回答后，用这个 id 取回现场接着干。这是"等待零消耗"的实现方式——三天没人回，这三天就没有进程在跑、不花 token。

另外有个行为细节：**拒绝之后 Agent 要退化**，改成给建议步骤、升级人工，而不是重试或者换个措辞再试。否则审批就成了摆设——反正拒了它还会再问。

如果追问"审批人疲劳怎么办"，我的答案是分级：低风险动作（只读、查询）自动放行，中风险单条确认，高风险双人复核；再配合事后抽样审计。**不能靠"每条都问人"，那等于没设计。**

# 收尾：三个故事怎么串起来（开场 30 秒用）

> "我做了三个 Agent 项目，刻意让它们各验证一个工程问题：
> **stock-insight 验证质量能不能被度量**——我把解析失败率从 54% 变成结构性不可能，同时发现 function calling 其实更贵；
> **column-writer 验证成本能不能被控制**——长文拆成可独立返修的单元，用四种模式横向比成本和质量；
> **sre-oncall 验证行为能不能被约束**——修复动作默认拒绝，模型只有提议权；需要人拍板时挂起，人回来用原现场续跑，等待期间零进程零 token。
>
> 三句话：**质量可测、成本可控、行为可控**。这三件事恰好是 AI 应用从 demo 走到生产必须过的三道关。"
