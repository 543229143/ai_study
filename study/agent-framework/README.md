# 三闸法（SEG：Slice / Evidence / Gate）

一套让 AI 编码代理**长期、稳定、可审计**地改代码的框架。

核心只有三样东西：**规则**（`AGENTS.md`）、**计划**（`docs/plan.md`）、**记录**（`docs/checkpoints/`）。
其余文件都是这三样的模板和说明。

---

## 一句话

> 不指望模型记住，把记忆和判断都搬到模型外面；
> 每片活都要能切、能验、能签字。

---

## 目录

| 文件 | 用途 |
| --- | --- |
| `AGENTS.md` | 项目级规则，直接复制到仓库根。**刹车都在这里** |
| `workflow.md` | 一轮的完整时序：定向→选片→实现→验证→记录→闸门 |
| `PROMPT.md` | 循环模式下每轮喂给 agent 的提示词 |
| `templates/plan.md` | 验收项清单模板（任务切分器） |
| `templates/task-card.md` | 单片任务卡（目标/边界/判定/回滚） |
| `templates/checkpoint.md` | 每片结束的记录模板 |
| `failure-modes.md` | 十种典型抽风与对策，**最值得先读的一页** |
| `scripts/init.sh` | 一键装进项目（幂等，不覆盖已有文件） |
| `scripts/loop.sh` | 可选的无值守循环，带熔断，默认关闭 |

---

## 四个部件

| 部件 | 干什么 | 落在哪 | 解决什么毛病 |
| --- | --- | --- | --- |
| **外置状态** | 计划、进度、经验放 git，不放在上下文里 | `plan.md`、`checkpoint`、git log | 上下文一长就飘、开始编 |
| **切** Slice | 用"可判定的验收项"倒逼任务变小 | `plan.md` 的 `- [ ]` 条目 | 一片改一堆，无法 review |
| **验** Evidence | 每片必须留下别人能复核的证据 | 测试输出、命令、SHA、截图 | 把计划说成完成 |
| **闸** Gate | 人签字才能进下一片 | checkpoint 里的"通过/不通过" | 无限修、范围蔓延 |

外置状态是底座，切、验、闸是三道闸门。缺任意一道，长跑就会退化成"看起来很努力"。

---

## 三个文件怎么流转

```
docs/plan.md            一条待办：标题 + 判定证据          ← 人写
   ↓ 开工时（只有中片以上才需要）
docs/tasks/T01.md       任务卡：边界 / 陷阱 / 回滚 / 预估   ← agent 展开，人确认两栏
   ↓ 完成后
docs/checkpoints/T01.md 证据 + 缺口 + 失败 + 下一步         ← agent 写，人签字
```

| 产物 | 谁生成 | 谁确认 | 什么时候要 |
| --- | --- | --- | --- |
| `plan.md` 条目 | 人（agent 可起草） | 人 | 每一片 |
| `task-card` | **agent 从 plan 条目展开** | 人确认「完成判定」「禁止碰」 | 半天以上的片 |
| `checkpoint` | agent | 人签字 | 每一片 |

**小片（1 小时内）不生成任务卡**，`plan.md` 里那一行就是卡——两处写同样字段只会互相打架。

### 任务卡怎么生成

中片以上，开工前给 agent 这一句：

```
读 docs/plan.md 里的 T01，按
/Users/zhaoxin/code/ai/ai_study/study/agent-framework/templates/task-card.md
展开成 docs/tasks/T01.md。

要求：
- 「完成判定」原样沿用 plan 里的命令，不许改
- 补全「禁止碰」「验收陷阱」「回滚」「预估」
- 不要写实现步骤
```

产出 `docs/tasks/T01.md` 后，你只改两栏（完成判定、禁止碰），然后开工。

**为什么不让 agent 自己定判定**：验收标准不能由被验收方单独定义。
它可以起草，但拍板必须是人——这是整套框架唯一的分权点。

## 安装与第一轮（10 分钟）

### 1. 装进项目

```bash
/Users/zhaoxin/code/ai/ai_study/study/agent-framework/scripts/init.sh ~/code/your-project
```

写入 `AGENTS.md`、`PROMPT.md`、`docs/plan.md`，建 `docs/checkpoints/`、`docs/tasks/`、`docs/design/`、`docs/contracts/`，
并把 `tmp/`、`.local/` 加进 `.gitignore`。幂等，不覆盖已有文件。

### 2. 写第一条

打开 `docs/plan.md`，把「现在做」改成你的第一条：

```markdown
- [ ] **T01** 给 /health 接口加数据库连通性检查
  - 判定证据：`pytest tests/test_health.py -q` → `3 passed`
  - 只改：`app/health.py`、`tests/test_health.py`（不碰迁移和配置）
  - 依据：`docs/design/health.md 2.1`
  - 回滚：`git revert <sha>`
```

**写不出判定就先别开工。**

### 3. 跑一轮

```bash
cd ~/code/your-project && codex exec < PROMPT.md
```

没有 `codex` 就把 `PROMPT.md` 直接粘给任何 agent。

### 4. 看三样

```bash
git log --oneline -3
git show --stat HEAD            # 有没有超范围
git show HEAD -- docs/plan.md   # 勾掉了没
```

四问：证据对得上吗？跳过测试了吗？超范围了吗？下一步具体吗？
**四问都过 → 下一片；任一不过 → 同一条退回。**

### 常见卡点

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| agent 说"任务不明确" | plan 里还是占位 | 填成第 2 步那种格式 |
| 一次改了一大堆 | 没写「只改」 | 补边界，对一眼 diff |
| `loop.sh` 说工作区不干净 | 上一轮没提交 | 提交或 `git stash` |
| 循环 2 轮退出（码 2） | 熔断，在原地打转 | 看这条是不是不可完成 |
| 说"已完成"但没证据 | 没填判定证据 | 补命令，重跑 |

### 3 分钟自测（不花 token）

```bash
T=$(mktemp -d) && cd $T && git init -q
git config user.email a@b.c && git config user.name t
/Users/zhaoxin/code/ai/ai_study/study/agent-framework/scripts/init.sh "$T" >/dev/null
git add -A && git commit -qm init && git checkout -qb feat/x

AGENT_CMD=true /Users/zhaoxin/code/ai/ai_study/study/agent-framework/scripts/loop.sh
# → 计划为空：退出 0

printf '\n- [ ] T01 测试条目\n' >> docs/plan.md && git commit -qam task
AGENT_CMD=true MAX=3 /Users/zhaoxin/code/ai/ai_study/study/agent-framework/scripts/loop.sh
# → 连续 2 轮无产出：退出 2（熔断）
```

## 第一周怎么落地

### 今天（30 分钟）

1. 装好（上一节第 1 步）
2. 改 `AGENTS.md` 三处：**边界**填你的生产环境和禁改目录、**验收**填真实能跑的命令、**语言**填提交规范
3. 写第一条验收项：挑一件本来就要做的小事，强制写出「判定证据」
   —— 写不出来就换一件，说明它还没想清楚

### 本周（每天 1 小时）

4. **手动跑 3 片**，不开循环
5. 每片都让 agent 写「下一步」，即使你已经知道 —— 这是给中断兜底
6. 第 3 片结束后复盘四问：
   - 哪一片切太大了？
   - 哪次验收其实不可判定？
   - 哪次它偷偷改了范围？
   - 哪次我签字太快了？

### 稳定后再考虑

7. 开循环（`MAX=3` 起步）
8. 熔断已内置：连续 2 轮无提交自动停
9. 把 checkpoint 收进 PR 描述，让 review 直接看证据

### 跑偏的三个信号

| 信号 | 说明 | 该做什么 |
| --- | --- | --- |
| checkpoint 越写越短 | 你在走过场 | 停下来，补证据 |
| 同一片反复"部分通过" | 切分有问题 | 拆成两片 |
| 你开始不读 diff 了 | 闸门失效 | 立刻停循环，回到手动 |

> 框架跑起来的标志不是"agent 变快了"，
> 而是**你敢在它干活的时候去干别的，回来只需要看证据**。

## plan 要写多长？技术文档放哪？

三层，各管一件事。**短的是索引，不是全部信息。**

| 层 | 文件 | 写什么 | 长度 |
| --- | --- | --- | --- |
| 索引 | `docs/plan.md` | 标题 + 判定证据 + 边界 | **3~5 行/条** |
| 展开 | `docs/tasks/T01.md` | 背景 / 现状 / 相关文件 / 陷阱 / 回滚 | **半页~1 页** |
| 深水 | `docs/design/<名字>.md` | 接口契约、数据模型、并发、迁移 | 1~3 页，按需 |

`plan.md` 短，是因为它只回答两个问题：**下一件做什么、怎么算做成了**。
排序和状态需要一个能一眼扫完的列表——写满技术细节就扫不动了。

### 大设计文档怎么变成 plan 条目（滚动拆分）

**不要一次拆完。** 拆得越远，猜得越多；做到第 4 条时现实一变，后面 36 条全废。

两层结构：

```markdown
## 里程碑（稳定，5~8 个）

1. 能导入 CSV
2. 能导入 Excel
3. 错误码统一

## 现在做（1 条，写到能直接开工）

- [ ] T01 读 UTF-8 CSV，输出 3 行 JSON
      怎么验：python -m app.import samples/a.csv → 3 行 JSON
      改哪里：app/import/csv.py
      依据：docs/design/import.md 2.1

## 接下来（最多 2 条，可以粗糙）

- [ ] T02 GBK 编码
- [ ] T03 列数不对返回 E01
```

规则：

- 里程碑从文档一次性切出，基本不变
- 「现在做」永远只有一条，且带可执行验收
- 「接下来」两条，轮到它时再细化
- **`plan.md` 全文不超过一屏**

例外：任务纯机械、拆的过程不会发现新信息（例如给 30 个接口加同一行日志），那就一次全拆，反而省事。

判断标准：

> 拆的过程中会不会发现新信息？
> 会 → 滚动拆；不会 → 全拆。

**设计文档是母本，不动；`plan.md` 是当前视图，随进度移动。**

### plan 这么短，agent 怎么知道要做什么

它实际拿到的是四样东西：

```
AGENTS.md          规则与边界
docs/tasks/T01.md  背景、现状、相关文件、验收陷阱
项目代码            它自己去读（守则要求"下手前先搜代码"）
对话                你当场的补充
```

**你觉得它信息不够，通常缺的不是字数，是「现状」和「相关文件」。**
所以任务卡里专门加了「上下文」一栏——这比把 plan 写长有效得多。

### 技术文档为什么不替代任务卡

不是不能写，是**不能拿它当验收标准**。

| | 技术文档 | 任务卡 |
| --- | --- | --- |
| 回答 | 怎么做 | 什么算做完 |
| 失效速度 | 快（改动就让步骤过时） | 慢（判定很少变） |
| 过时后果 | agent 照抄错误方案 | 只会让判定变严或变松 |

两份都写实现步骤 → **必然不同步** → agent 开始相信文档而不信代码，这是最贵的坑。

所以正确做法是：**技术文档写约束，任务卡引用它。**

### 技术文档什么时候必须写

- 对外接口契约（前后端、上下游）
- 数据模型 / 迁移 / 不可回滚操作
- 并发、幂等、顺序
- 多人并行改同一模块
- 需要别人接手维护

写的时候就写这四样：**边界、判定、回滚、隐含约束**。

**不要写**类图、时序、函数签名草案、实现步骤——它们在写代码的十分钟内就会被推翻，而且最容易被 agent 当成"必须照抄"。

判断标准：

> 下一个 agent 不看文档、只看代码和测试，能不能接着干？

能 → 不用写。不能 → 缺的通常不是"更详细"，而是**缺一条能跑的验收命令**。

设计文档适合"事前对齐"，不适合"事后追溯"；追溯用 checkpoint。

## 复杂项目：多出来的三样约束

**项目变复杂，不是把规则写长，是补三个缺的东西。**

| 默认假设 | 复杂项目现实 | 补什么 |
| --- | --- | --- |
| 一片能在一小时内做完 | 有些片要跨天、跨模块 | **契约**：写清哪些不能变 |
| 一条命令能证明做完了 | 要分单元/集成/真实/回归 | **验收矩阵**：哪层跑哪些 |
| 一个人一次做一片 | 多片并行、多人协作 | **片状态机**：谁在改什么 |

这三样都是往现有文件里加内容，不新增文档。

### 一、契约文档（`docs/contracts/<模块>.md`）

**解决"agent 不知道哪些东西不能动"。**

代码能告诉 agent 现在长什么样，但告诉不了它"这个字段下游在用，不能改名"。
这类信息只在人脑子里，必须写下来。

只写这五样：

```markdown
# 契约：健康检查接口

## 输入输出
- `GET /health` → 200 `{"status":"ok","db":"ok|fail"}`
- 不允许改字段名，`db` 的值只允许 ok/fail

## 错误码
- db 不可用 → 仍返回 200，`db: "fail"`（不返回 5xx，监控依赖状态码）

## 幂等与超时
- 幂等；db 探测超时 2s，超时视为 fail

## 数据所有权
- 只读 probe 查询，不写库

## 谁依赖它
- K8s liveness probe、外部监控、/status 聚合页
```

**不要写**类图、时序图、函数签名、实现步骤——写了就会过时，过时就会被照抄。

何时必须写，见上一节的四类场景。一个模块一份，改动前先改契约，再改代码。

### 二、验收矩阵

**解决"跑测试通过"这句话没有信息量。**

在 `docs/plan.md` 顶部放一张表：

```markdown
| 层 | 命令 | 何时必须跑 |
| --- | --- | --- |
| L1 单元 | `pytest tests/unit -q` | 每一片 |
| L2 集成 | `pytest tests/integration -q` | 碰了接口/DB/序列化 |
| L3 真实 | `docker compose up -d && ./scripts/smoke.sh` | 碰了运行时/配置/依赖 |
| L4 回归 | `pytest -q` | 每片合并前 |
| L5 人工 | 页面点一遍 / 看一次日志 | 面向用户的改动 |
```

任务卡里写「本片验收：L1 + L2 + L4」，而不是写"跑一下测试"。

分层的好处：

- 让"没跑 L3"变成**明确声明**，而不是含糊的"验证过了"
- 让 agent 知道边界：改个内部函数不用起整套环境
- checkpoint 逐层打勾，人一眼看出缺哪层

### 三、片状态机 + 一写者原则

**解决"多片并行时互相覆盖"。**

```markdown
- [ ] T01 健康检查加 db 探测        doing   @liming
- [ ] T02 慢查询日志                todo
- [ ] T03 健康检查加超时            blocked  等 T01 的契约确认
```

三条规则：

1. `doing` 的数量 ≤ 并行人数。一个人不要同时开三片。
2. **同一文件同一时间只有一片在改。** 冲突不是 merge 时解决，是开工前避免。
3. `blocked` 必须写清等什么，否则一周后没人知道为什么停着。

分支约定：`feat/T01-health-db`，一片一分支，合并前过验收矩阵。

### 复杂项目的一天

```
上午
  看 plan：doing 有几条、blocked 在等什么
  选一条 todo → 改契约（如需）→ 展开任务卡 → 交给 agent
  agent 跑 L1/L2，报结果

中午
  你看 diff + 证据 → 签字或退回

下午
  重复 1~2 次
  收尾：plan 状态更新、blocked 写明原因、checkpoint 提交
```

**一天 2~3 片是正常速度。** 一天十片通常说明片切错了，或验收放水了。

### 四个常见错

| 错 | 后果 | 改法 |
| --- | --- | --- |
| 先写大而全的设计文档 | 写完就过时，agent 照抄 | 只写契约，且只写约束 |
| 多片同时 `doing` | 互相覆盖，越修越乱 | 一文件一写者 |
| 用"测试通过"当验收 | L3/L5 从来没跑过 | 验收矩阵逐层声明 |
| 片切得太大 | 一次改 20 个文件，无法 review | 切到"能独立验证"为止 |

### 什么时候需要加码

| 你的情况 | 要加什么 |
| --- | --- |
| 改动局部、单人维护 | 只用到本文为止 |
| 跨模块、有下游、有外部系统 | 加 `templates/task-card.md`（契约 + 边界） |
| 多人并行、要审计、不可回滚 | 再加 `workflow.md` 的闸门 + `AGENTS.md` 的停止信号 |

**升级路径是加约束，不是加文件。**

---

## 三条硬规则

1. **写不出"判定证据"的任务，不许进 plan**
   （写不出 = 切不动 = 一定会烂尾）
2. **mock / 单测通过不算验收**
   （除非这一片的验收标准就是单测）
3. **失败要原样留在记录里**
   （编译错误、跳过项、超时，全部保留；这比"全绿"更可信）

---

## 写规则的原则：定义 > 禁止

规则只保留**能被机械判定**的。原因：道德训诫对模型无效，定义才有效。

| 别写 | 改写成 |
| --- | --- |
| 不许报喜 / 要诚实 | 完成 = 证据 + 记录 + 签字；缺一即"未验证" |
| 不许无限修 | 三条停止信号：原地打转 / 越修越糟 / 超大预估时间 |
| 不要偷懒 | 每片必须贴出验证命令与输出 |
| 注意质量 | 明确"什么不算验收"（mock、截图、类型检查） |

判断方法：**这条规则违反时，能不能被指出来？** 不能，就删掉或改写成定义。

副作用提醒：只写"禁止"会逼模型走向另一个极端——每句话都加"可能未完全验证"。**过度免责和虚假完成一样没用。**

---

## 不适合的场景

- 探索性调研（没有明确验收项）
- 一次性脚本（切片的开销大于收益）
- 高风险生产变更（需要更重的人工评审，不是这套能替代的）
