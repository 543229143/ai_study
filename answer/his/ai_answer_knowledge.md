# AI 应用开发 技术问答

> 精简口述版，一问一答，适合快速回顾。像聊天不是背稿。

---

## 一、基础认知

**Q：大模型应用开发具体做什么？**

**A：** 用大模型的能力搭企业应用。比如智能客服、知识库助手、业务 Agent。核心工作包括模型接入、提示词设计、RAG、工具调用、系统架构和效果评估。一句话：把大模型的能力落地到具体业务里。

**Q：和传统 Java 开发最大的区别在哪？**

**A：** 不确定性。传统系统的输入输出是固定的，但大模型每次回答都可能不一样，没法保证它次次说对。所以要在系统层面加各种机制——检索、约束、兜底、评估，把概率性的输出变得可靠。核心难点不是调模型，是把不确定性变成确定性。

**Q：Prompt 工程做过哪些优化？**

**A：** 几个手段。第一，分层设计，系统指令、知识素材、用户提问分开，结构清晰；第二，输出格式约束，要求按固定格式返回，方便后端解析；第三，Few-shot 示例，加几个标准问答例子统一输出逻辑；第四，对内对外的 prompt 分开，精准控制严谨度和话术风格。

**Q：Prompt engineering 和 context engineering 什么关系？**

**A：** 两回事，配合着用。prompt 管的是"怎么说"，context 管的是"让模型在这一轮看到什么"。不是替代关系。

## 二、RAG 核心

**Q：RAG 的工作原理是什么？**

**A：** 检索增强生成。用户提问后，系统先把问题转成向量，到向量库里检索相关知识，找到后把资料和问题一起发给大模型，模型基于真实资料回答。完整链路：文档采集 → 文档解析 → 切片 → 向量化 → 入库 → 用户检索 → 组装 prompt → 模型生成。RAG 解决的是知识时效性问题，不是模型能力问题。

**Q：为什么不能把企业资料全部放到 prompt 里？**

**A：** 三个原因。第一，上下文再长，塞大量无关内容进去，模型精度反而会下降，关键信息容易被淹没；第二，token 成本扛不住，每次请求都把所有资料塞一遍，量太大了；第三，响应速度会变慢，prompt 越长首 token 延迟越高。所以不是让模型记住所有知识，而是需要的时候能检索到正确的资料。

**Q：怎么区分普通问答和需要 RAG 检索的问答？**

**A：** 做了前置分类。通识问题、闲聊、基础常识，直接调大模型回答；涉及公司业务、规章制度、内部规范的，自动触发 RAG 检索，保证答案有据可依。

**Q：向量化是什么？**

**A：** 把文本转成计算机能算的数字向量。比如"如何申请退款"和"订单取消怎么退款"，文字不一样但语义相近，向量化模型会把它们转成距离近的向量。检索时就不是匹配关键词了，而是理解语义。

**Q：为什么不用 MySQL 的 LIKE 查询？**

**A：** LIKE 只能精确匹配关键词，但用户的表达方式太多变了。用户问"钱什么时候能退回来"，资料写的是"退款周期一般是三到七个工作日"，关键词完全不沾边。生产环境一般关键词检索加向量检索，再加重排，召回准确率才够。

**Q：企业内部文档格式很杂，怎么统一处理？**

**A：** Word、PDF 用工具提取纯文本，扫描件和图片类 PDF 走 OCR 识别。所有文档解析完了统一清洗，去掉页眉页脚、空行、乱码、水印这些无效内容，然后统一切片、向量化、入库。核心原则：进来的垃圾，出去也是垃圾。

**Q：文档切片大小一般怎么设？**

**A：** 日常业务文档一般按 300 到 800 字符切，配上 10% 到 20% 的重叠。切片太短会把完整逻辑拆散，模型理解不了上下文；切片太长 token 占用高，冗余信息多，还容易带进去无关内容干扰判断。中文场景尤其要注意，300 字的中文信息量比英文大得多。

**Q：重叠切片越多越好吗？**

**A：** 不是。重叠太小容易丢关键信息，重叠太大切片冗余严重，入库数据量大，检索成本也高。生产环境一般控制在 10% 到 20%，平衡准确率和性能。

## 三、检索进阶

**Q：RAG 整个链路里，检索这块是怎么优化的？**

**A：** 核心思路是"粗筛加精选"。先把口子开大，保证相关文档都被捞回来，再用高精度的模型把最相关的筛出来喂给大模型。从源头上减少幻觉，比在模型端修修补补有效得多。

**Q：向量数据库各自适合什么场景？**

**A：** 本地测试用轻量级的就行，不用额外部署。中小规模生产用单机版的，部署简单好维护。海量文档高并发场景用分布式集群，支持分片扩容和数据持久化。

**Q：多路召回加重排的方案，怎么理解？**

**A：** 就是一个漏斗模型。多路召回负责把口子开大，保证相关的都能捞回来，宁可错杀一千不放过一个；重排负责在底部做最后把关，用高精度模型把最相关的 Top3 到 Top5 筛出来喂给大模型。两件事分工明确，各有各的价值。

**Q：为什么不直接用向量模型做重排？**

**A：** 向量模型是 Bi-encoder，速度快但匹配精度有限。重排用的 Cross-encoder 是把问题和文档拼在一起做全量交互，精度高很多但速度慢。所以 Embedding 做初筛，Rerank 做精排，各司其职。

**Q：两路检索各自适合什么场景？**

**A：** 向量检索适合语义匹配，比如"怎么申请退款"能召回语义相关的退款流程。BM25 这种传统检索适合精确匹配，比如订单号、身份证号这些需要完全命中的内容。两路互补，缺一不可。

**Q：RRF 算法是做什么的？**

**A：** 倒数秩融合。核心作用是把两路检索的结果按排名位置做加权融合，不会让某一路的结果完全主导最终排序。比简单地把结果拼在一起效果好很多。

**Q：检索出来多条文档，怎么判断优先级？**

**A：** 做了三层排序。第一层向量相似度粗召回；第二层用重排模型精准判断关联度；第三层加自定义权重规则，核心制度和最新文档优先级高，老旧的降权。最后截取优质的 TopN 传给模型。

**Q：嵌入模型怎么选？**

**A：** 通用业务用通用中文模型就行，性价比高响应快。金融、政务这种专业领域用领域专项的，语义匹配精度更高。生产环境选稳定性好、向量维度和向量库能适配的。

**Q：召回不准的常见原因有哪些？**

**A：** 主要有四点。第一，文档切片不合理，内容碎片化或冗余太多；第二，嵌入模型和业务不匹配；第三，用户提问太口语化、表述模糊；第四，缺少重排环节，弱相关内容干扰了精准召回。

**Q：检索出来的内容很多，但回答反而变差了，怎么解决？**

**A：** 核心原因是弱相关和冗余的片段干扰了模型判断。两点优化：一是加重排模型过滤无效内容，只保留 Top3 到 Top5；二是做切片内容去重，剔除相似的冗余片段。保证传进去的信息精准有效。

**Q：重排模型的精度和速度怎么平衡？**

**A：** 生产环境先靠多路召回把结果压缩到 100 篇以内，再用重排模型去处理。并发高的话给重排加缓存，重复的问题不用重复打分。

## 四、效果保障

**Q：RAG 能不能解决幻觉问题？**

**A：** 能大幅降低，但不能完全根除。多路召回保证了相关资料都能被找到，重排筛出了最相关的内容，模型基于真实资料回答就不会凭空编造。但模型还是可能曲解资料或过度推理，所以还需要其他手段配合。

**Q：除了 RAG，还有哪些降低幻觉的手段？**

**A：** 几个层面。第一，prompt 里强制约束，没有相关资料就说不知道，禁止编造；第二，输出校验，把回答里的关键信息抽出来反向去知识库核对；第三，调低 temperature，降低生成随机性；第四，前接分类模型，知识库外的问题直接拦住，不走大模型。多管齐下，效果才稳。

**Q：怎么做上下文多轮对话？**

**A：** 对历史对话做了摘要压缩。用户第二轮提问时，系统结合上文语义重构出完整问题再去做检索，不会断章取义。多轮连贯性的关键是让模型理解"用户现在问的到底指什么"。

**Q：RAG 和微调怎么理解？怎么选？**

**A：** RAG 是外挂知识库，数据实时更新，不改模型权重，答案能溯源，适合大多数企业场景。微调是改模型本身的参数，适合固定话术和输出风格。企业落地优先用 RAG，灵活成本低；需要统一输出风格时，用微调辅助。见过不少上来就想微调的，其实先用好 RAG 已经够用。

## 五、工程落地

**Q：传统 Java 系统接 AI，难点在哪？**

**A：** 传统系统是确定性逻辑，AI 是概率性输出。接进来要兼容各种异常——模型超时、检索没结果、回答不规范。同时要做数据隔离，防止企业私密资料外流，还要适配原有权限体系。最大的误区是把 AI 当成普通 API 来调。

**Q：微服务经验怎么用在 AI 系统上？**

**A：** 拆成多个独立服务，文档解析、向量检索、大模型网关、问答业务，每个职责清晰，完全解耦。微服务那套成熟的方案——服务注册发现、熔断限流、日志链路追踪——都能直接用。单独封装一个大模型网关，集中管密钥、计费、鉴权，换模型也方便。

**Q：只调 API 和真正做 AI 应用开发，差距在哪？**

**A：** 只调 API 只能做演示问答，落不了地。真正的 AI 工程化要打通文档处理、向量检索、数据治理、限流容错、成本管控、权限安全、效果迭代一整条链路。这套工程化能力才是资深后端开发的核心竞争力。

**Q：怎么防止用户越权查询？**

**A：** 入库和检索两层都做了权限管控。文档入库时绑定部门、角色、权限标签；检索时携带权限信息过滤结果，只能召回权限范围内的资料。

**Q：模型调用超时、报错、重试怎么处理？**

**A：** 按后端工程化的思路来。配置超时时间、自动重试加熔断降级。异常时给用户友好提示，同时完整记录日志和链路。系统不能崩，体验不能受影响。

**Q：线上 RAG 并发高的时候有什么瓶颈？怎么优化？**

**A：** 三个瓶颈。向量检索耗时长、模型接口调用排队阻塞、重复提问造成重复向量化计算。优化手段：热点结果做本地缓存；向量库建索引加速检索；向量化做成异步处理；模型接口加队列限流。另外还有一个容易被忽略的点——成本。很多人只看 token 单价，但线上真正的瓶颈是 KV Cache 占显存，上下文越长并发越高，显存消耗越厉害，首 token 延迟跟着飙升。

**Q：从零设计一个 Agent 系统，怎么做？**

**A：** 按几个步骤走。先定边界，哪些走 workflow 哪些用 agent；选模型，按任务类型、延迟、成本匹配；设计工具，最小权限原则，名称清楚参数结构化；搭运行环境，状态机加工具执行器加异常处理；加治理，人工介入和审计日志；配记忆，临时状态、长期记忆、用户偏好分开管，难的不是存而是存什么、什么时候读写、怎么让它失效；最后做评测，按链路拆指标，不能只看答没答对。

**Q：线上怎么判断系统好不好？**

**A：** 不能光靠感觉。离线测召回率准不准、回答有没有瞎编；线上埋点记录用户反馈，点赞点踩纠错都能收集。每周出一份质量报告，拿数据驱动优化。不靠猜，靠数据。

**Q：讲一个你排查过的线上问题。**

**A：** 上线第一周，运营说某合同条款怎么都搜不到。查了日志，入库正常，向量检索也返回了结果，但重排之后被过滤掉了。后来发现合同模板有个"本页无正文"的占位符，切片以后和正文混在一起，重排模型把它判为无关。修了清洗规则，这种占位符提前过滤掉，问题就解决了。很多线上问题不是模型的问题，是数据的问题。

## 六、核心认知

**Q：AI 应用开发最核心的工程难点是什么？**

**A：** 不是调模型，而是怎么把大模型的不确定性，通过工程手段变成企业可用的确定性。靠数据治理、检索优化、异常容错、权限管控、成本管控这些手段，让 AI 系统稳定、安全、低成本地落地。这恰恰是后端工程师转型 AI 开发最大的优势——AI 应用最终还是软件工程。

## 七、Agent Skill 与平台化

**根本区别：约束的执行权在谁手里。**

- **Skill**：约束写在提示词里，是建议——跑不跑、跑成什么样，由模型决定，系统不保证。单次效果可以做得很好，但下限靠自觉、确定性随模型漂移、改流程靠祈祷。
- **平台**：约束写在代码里，是强制——工具注册、权限、状态、恢复都在代码路径上，模型只影响决策，不影响流程。买的是确定性、可观测性、可演进性。

**Q：Agent Skill 和平台化有什么区别？**

**A：** 一个教模型怎么干活，一个保证系统不出乱子。Skill 是说明书，把流程和知识打包给模型，约束写在提示词里，听不听靠模型自觉；平台把约束写成代码，工具、权限、审计、断点恢复都由系统保证。核心区别一句话：约束的执行权在谁手里——Skill 靠自觉，平台靠强制。

**Q：Skill 做好点，是不是就够了？**

**A：** 单次效果差不多，但差三样：下限（模型跑偏没兜底）、确定性（换模型效果就漂移）、演进（改流程是改文档，没法测）。平台买的不是单次准确率，是确定性、可观测性、可演进性。

**Q：那 Skill 还有用吗？**

**A：** 有用，俩是分层不是替代。Skill 传播经验成本最低，一个文件夹任何人拿去就能用，先在 skill 里把流程跑通验证，再固化成平台代码——所以 skill 是流程设计器，平台是流程固化器，知识吸收进平台，控制交给系统。

一句话：skill 是菜谱，平台是中央厨房，厨房的标准化也得从一份好菜谱开始。
